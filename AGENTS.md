# Project implementation rules

- Client purchasing/invoicing links retain companies.purchasing_invoicing_user_id as master ownership; guarded order writes resolve timed operational_leave_cover, with transactional changes and scheduled restoration excluding completed_date and completed/delivered/cancelled records; never modify reps or fulfillment assignments. Why: leave cover must preserve master links and settled records, and end without an app visit.
- Workshop timers use validated, serialized commands behind a public invoker/private definer boundary; show the paginated finished-session ledger and total hours on every job, using saved rate snapshots for recorded labour; fabrication completion reloads paginated cost/PDF entries explicitly. Timer completion is independent of job completion. Why: concurrent devices must not double-count work, hide saved hours, reprice historical labour or bypass technician ownership.
- Workshop lists, comments and shared timer ledgers use useLiveData recovery, paginated stable reads and latest-read guards; deleted details close after refresh. Shared comment reads batch reactions and preserve the latest-60 overview. Workshop email reads paginate and fail before sending on errors. Why: missed events, row caps and overlapping reads must not leave users viewing different saved data.
- Route exports split all stops into mobile-compatible numbered Google Maps legs; Waze links target individual stops. Why: long routes must never silently omit destinations.
- Portal reorders retain original company/order/item identities in validated staff-review requests and company-scoped RLS; portal and staff reads use paginated, bounded original-order item reads, with requested quantities and unavailable-item feedback; reviewed/accepted/declined requests remain read-only and inspectable. Timers capture fabrication hours once with rate snapshots. Why: self-service must not create supplier orders, hide the client's request or reprice historical labour.

- Order bulk status changes share item-counter updates and verify affected rows; assignment verifies returned assignees, not just IDs, without bypassing client ownership or timed delegation. Selection uses unique filtered order IDs across lanes. Why: board positions derive from quantities and denied or overridden writes must not report success.
- Shared stop assignment batches treat conflict-cancelled saves as failures and keep selection. Why: a handled conflict is not confirmation that the chosen assignee was saved.

- Dispatch On route entry uses revision-checked saves; receipts retain On route until the idempotent finish_dispatch_route_stop RPC derives full/partial/none from cumulative quantities. Why: explicit completion must not invent deliveries or let source refreshes remove unchecked stops.

- Keep the centred operational popup entrance animation in the global theme so Orders, Collections, Deliveries, and other order surfaces share identical motion.
- Position custom right-click menus with the shared viewport-aware hook so they flip and remain fully visible near every screen edge.- Comment push: notifications INSERT trigger -> send-push edge fn (VAPID web push, claims row via pushed_at); SW push handlers live in public/push-sw.js imported by workbox; native app uses local notifications while open. Why: one pipeline for every device.
- Windows app: desktop/ Electron shell loading the live site, built to an NSIS .exe on windows-latest in the same workflow and attached to the same GitHub release as the APK. Why: real installer that always stays up to date, and releases/latest serves both files.
- Fabrication projects: fabrication_* tables + private fabrication-files bucket (signed URLs); A4 PDF built client-side in src/lib/fabricationPdf.ts. Why: one self-contained workspace that prints without a server.
- Buying Sheet: procurement helpers calculate demand net of received and Zoho-invoiced units, and pool open-PO units (from zoho_document_cache via get_buying_sheet_live_coverage) once per SKU oldest-first; all views share row-key selection, and reads use bounded pagination. Why: prevent duplicate purchasing without Zoho API calls.
- Buying Sheet uses app-level fullscreen below portalled dialogs and menus; copy actions use awaited clipboard fallback and explicit error feedback. Why: keep notes, emails and actions usable in browser and app views.
- Native lifecycle, Android Back and comment notification listeners mount at the app shell; device opt-out overrides OS permission, and missing native plugins require an APK update. Why: behavior must remain consistent across workspaces and Settings without claiming foreground alerts are remote push.
- Commission profit-split rules and cost-basis caps live in src/lib/commissionRules.ts and are mirrored in the rep-commission-data edge function; test both calculations together and bump report_version when rules change. Why: client overrides and server reports must agree and stale caches must recalc.
- Commission vendor costs use exact text then stable item identity in costMatching.ts; shared generic products cannot use SKU/ID fallback, and incomplete bill reads must not overwrite reports. Why: prevent missing or unrelated costs from changing payouts.
- Commission vendor bills are read once into commission_bill_cache (keyed by bill_id + last_modified_time) with retried, time-budgeted Zoho reads; an unfinished read keeps progress and the page auto-continues. Why: Zoho drops long bill scans, which left stale description-only reports.
- Commission report cache reuse requires the current invoice-link fingerprint, including the refresh throttle; COD link saves read back ownership and request a normal report refresh. Why: saved invoice ownership must not be hidden by stale reports or admin-only forced refresh.
- Commission rep visibility: commission_rep_access limits non-admin users to listed reps (none = all); rep-commission-data scopes every response, and saved item costs are part of the cache fingerprint. Why: per-rep privacy and saved costs show immediately.
- Supplier price history reads saved commission_bill_cache lines through the approval-checked get_supplier_price_history RPC; no extra Zoho calls. Why: price warnings must not add Zoho load.
- Inventory refresh uses bounded inventory-only Zoho reads and merges under the webhook cache lock; per-SKU stockUpdatedAt, not cache fetched_at, controls freshness. Why: bill/PO events must not make stale stock look fresh, and failed scans must retain previous data.
- Stock shortage notifications are emitted by the saved-inventory trigger and deduplicated in system-owned stock_alert_state until fresh inventory confirms recovery; notification delivery reuses the existing push pipeline. Why: alerts must work without an open app, cannot be forged by staff, and must not repeat after dismissal.
